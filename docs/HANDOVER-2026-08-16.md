## ✅ RESOLVED: SendGrid / custom SMTP (the previous STEP 1)

Password reset delivers. A reset from production `/profile` at **18:19:15Z on
16 August** returned `POST /recover → 200` with no error field, and the message
arrived.

**The fault was never the scopes, domain authentication, or the toggle.** The
secret stored in Supabase's SMTP password field simply never matched the live
SendGrid key — logged every time as
`535 "Authentication failed: The provided authorization grant is invalid,
expired, or revoked"`. Re-entering the password fixed it. Nothing else changed.

Live key `*ASiLUMmagazine`, ID `coSM3vbvTPGpQLGYLJzE7g`, **Mail Send = Full
Access**, everything else No Access (inspected directly).

**Three corrections to the old verification advice**, all in `HANDOVER-2026-08-15`:

1. **`mail.send` is NOT the success signal under custom SMTP.** That event fires
   only when Supabase's *shared* sender delivers. The real signal is the
   **absence** of the `535` — `/recover` returning 200 with no `error` field.
2. **A blank password field after a cold reload proves nothing** (rendered blank
   by design). A `"reloading api with new configuration"` line in `auth_logs`
   is what proves a save landed.
3. **The middle segment of an `SG.` key is its key ID**, displayed permanently
   by SendGrid — so a stored password can be checked against the live key
   without the secret leaving the page.

## ▶ THE LESSON OF THIS SESSION: TWO TESTS THAT COULD NOT FAIL

This is the most transferable thing here, and it happened **twice in two
consecutive PRs**.

**Round 2, the booth roster.** The test fetched `/api/business?booths=1`,
iterated `booths`, and asserted each one's keys contained no `accountId`. It
passed against a route deliberately reverted to leak `accountId` — because with
no verified businesses the loop body never ran. Production has **0 booths**, so
it would have been vacuous there indefinitely. Fixed by **seeding** a verified
business and asserting the seed is present *before* checking shape.

**Round 3, the palette.** The test asserted the caller's bogus colour label was
**absent** from the response. That would still pass if the route stopped
returning a palette at all. Fixed by asserting **positively** that the
server-derived name **is** `"black"`.

**The rule:** never assert only an absence — assert the positive value too. And
**always run the revert**; it is the only thing that catches this class. Both
were caught that way and neither would have been caught any other way.

This is the same family as the trap already recorded from 15 August (a regex
using `[\s\S]*?` matching an unrelated `neighbors:` fifteen lines away). Three
instances now. It is the failure mode this codebase is most prone to.

### And its sibling: a green API test while the UI lies

Later the same day, the fix requiring an account to post to the wire **created a
worse bug than the one it closed**, and nothing but clicking the real button
found it.

`publish()` in `app/hotlist/page.js` wrote the post to `localStorage` *before*
the server answered, and its handler only ever asked whether the post was
`held`. So any refusal set the note to `""` and left the copy in place. Once
posting required an account, a signed-out visitor would watch their transmission
appear on their own wire, **with no error, having published nothing.**

The API returned a correct `403`. The new route tests passed. The build was
green. All three were true while the product silently lied to the user.

**So: an API-level test can pass while the interface it feeds is wrong.** When a
change alters what a route REFUSES, drive the control that calls it. The
`feature-verification` skill already says compiling is not completion; this is
the concrete case that proves why.

## Route coverage: 24 of 37, from a standing start

Before #205 **not one API route handler had ever been invoked** by the suite.
Six test files reached routes only by reading their source as text.

**The obstacle was one missing file extension, not architecture.** Route files
import bare `next/server`; Next 16 ships no `exports` map, so that specifier
resolves only through Next's bundler and is `ERR_MODULE_NOT_FOUND` under
`node --test`. `tests/helpers/next-resolve.mjs` retries a *failing* bare
`next/<subpath>` with `.js` appended.

**The harness** — `tests/helpers/route.js`:
- `callRoute(handler, opts)` builds a real `NextRequest`, calls the handler,
  reads the real `Response`. Nothing mocked: identity, rate limits, JSON
  parsing and the db layer all run. Supports `json`, `form` (real multipart
  `FormData`), `rawBody`, `query`, `cookies`, `bearer`, `context`.
- `newDevice()` mints a cookie the real `verifiedDevice()` accepts, fresh per
  test, so the routes' real quotas cannot leak between tests.
- **Routes must be loaded via `loadRoute()`, never imported statically** —
  static imports all resolve before any module body runs, so the resolve hook
  would not be registered yet.

**What the harness does not cover**, documented in the file: no Next routing (a
route registered at the wrong path still passes), no middleware, no cache
semantics, no network — so `sb-` identity is exercised only at the rejection
boundary.

**The 13 routes still unmentioned:**
`/api/asterisk/memory` · `/api/connect` · `/api/discover/rails` · `/api/ebay` ·
`/api/editorial/engage` · `/api/follow` · `/api/ingest` · `/api/measurements` ·
`/api/search` · `/api/style-profile` · `/api/stylist` · `/api/suggest` ·

## Traps learned this session

1. **A test that asserts only an absence can pass vacuously.** Twice. See the
   section above. Assert the positive value, and always run the revert.
2. **A green API test does not mean the UI is right.** When a change alters what
   a route refuses, drive the control that calls it — the wire composer showed
   no error and kept a phantom local post while the API correctly returned 403.
   Check the optimistic-write path of any control whose endpoint you just made
   stricter: writing local state before the server answers is a lie waiting for
   a refusal.
2. **Routes must be loaded via `loadRoute()`, not statically imported** — static
   imports all resolve before any module body runs, so the `next/server` hook
   would not be registered yet.
3. **Use `fileURLToPath`, never `url.pathname`, to build repo paths.** This
   repo's directory name contains spaces, so `.pathname` returns a
   percent-encoded string that `pathToFileURL` encodes a second time
   (`%20` → `%2520`) and the import fails.
4. **Shell-quoting mangles curl JSON payloads.** Two "discrepancies" between the
   harness and the real server were `\"user\"` inside double quotes producing
   invalid JSON → 400 instead of 401. Use `--data-raw` with single quotes before
   reporting a mismatch.
5. **Supabase auth logs are a rolling 24-hour window.** Evidence rolls off;
   capture timelines into a doc before then.
6. **SendGrid puts a Cloudflare CAPTCHA on re-login**, so Email Activity is
   owner-only — an agent cannot verify delivery there.

Still in force from before: every `supabase/schema-vN-*.sql` must insert its
version into `app_schema_migrations`; never export `DATABASE_URL` globally when
running tests (use `TEST_DATABASE_URL`); never force oversized viewports on the
shared preview pane; benchmark warm-vs-warm with medians across ≥3 runs; a test
can only catch a bug in the backend it runs against.

## Rituals (unchanged)

- Build/test: `export PATH="$HOME/.local/node-v20.18.1-darwin-arm64/bin:$PATH"`
  → `npm run build` / `npm test`. Postgres suite:
  `TEST_DATABASE_URL="$DATABASE_URL"` plus `DATABASE_SSL_CA`.
- Preview: launch config `asilum` (:3458). **It runs against the LIVE database
  and `next start` serves the BUILT app** — rebuild and restart to see edits,
  and keep verification read-only unless you intend to write to production.
- Stacked merges (A3): retarget child to `main` *before* merging, then verify
  with `git merge-base --is-ancestor`. Branches are retained.
- `gh pr edit` and `gh pr merge` hit the `read:org` scope wall on the stored
  token. Use the REST API:
  `gh api -X POST repos/.../pulls --input body.json`, and
  `gh api -X PUT repos/.../pulls/N/merge -f merge_method=merge -f sha=<head>`.
  **Wait for the `Production build` check** before merging — it lags the push.
- Migrations run as the OWNER role: `node scripts/apply-schema.mjs <file>` uses
  `DATABASE_ADMIN_URL`; the runtime `DATABASE_URL` (asilum_app) has no DDL.
- `pg_dump` / `psql` / `pg_restore` 18.4 live in `~/.local/libpq/18.4/`. Set
  `DYLD_LIBRARY_PATH=~/.local/libpq/18.4/lib`.
- Project skills live in `.claude/skills/` — load `asilum-architecture` before
  backend work, `asilum-ui` before any UI change, `database-safety` before
  touching Supabase, `algorithm-evaluation` before claiming a ranking change is
  an improvement, `feature-verification` when finishing. They are binding.
